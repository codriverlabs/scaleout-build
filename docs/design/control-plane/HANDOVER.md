### Switching runtime mode

Native mode is fully working — four native-only defects were found and fixed the first time it was
deployed (a static `SecureRandom` that GraalVM refused to bake into the image, and three gaps in
reflection metadata). It is not the resting state only because the resource-slimming work ended on JVM.

```bash
AWS_REGION=eu-west-1 ./scripts/deploy-local.sh --native --skip-agent --yes   # ~3 min, includes the image build
AWS_REGION=eu-west-1 ./scripts/deploy-local.sh --jvm    --skip-agent --yes   # ~30 s
```

Native is measurably better where it matters: cold start 441–464 ms against 2345 ms, peak memory 145 MB
against 237 MB. JVM is the CDK default because it needs no GraalVM toolchain, so a first deploy works from
a plain `mvn package`. Figures in [`lambda-resource-usage.md`](lambda-resource-usage.md).

**Native deploys the architecture of the machine that builds it**, because a native image cannot be
cross-compiled. From an x86_64 workstation that is `native/x86_64`. arm64 needs an arm64 builder;
`deploy.yml` already selects `ubuntu-24.04-arm` for that combination, so it is a CI run rather than a code
change. arm64 is the intended production target — 25% cheaper per GB-second.

### 2. Spring Boot AOT and Helidon are untested end to end

`ArgsFileDirectoryStrategy` covers both — they build through GraalVM's `native-maven-plugin`, which has a
`write-args-file` goal — but no real project has been through that path. It deliberately has **no default
argfile location**: `write-args-file` takes its path from `graalvm.native-image.args-file`, and a wrong
guess would not error, it would fall through to the derived strategy and produce a binary that builds
cleanly then misbehaves at run time.

The Quarkus route is the cautionary precedent: it looked correct until a real project proved it had never
worked on any current Quarkus version.

### 3. AWS SDK moves faster than review does

`awssdk.version` is `2.55.5`, verified latest at 2026-09-25 against Central's `maven-metadata.xml`
rather than against a quoted number. `#29` merged `2.55.1`; five patches shipped in the days since, and
two separate guesses at "latest" during that window (`2.55.2`, then `2.55.3`) were both already behind

Treat any version written here as stale on sight. The authoritative check, which does not depend on
remembering the right patch number:

```bash
curl -s https://repo.maven.apache.org/maven2/software/amazon/awssdk/bom/maven-metadata.xml \
  | grep -o '<latest>[^<]*' | cut -d'>' -f2
```

A BOM also needs `-Dpackaging=pom` when probing with `dependency:get`, or the resolution fails
misleadingly — it looks for a jar that does not exist and reports the version as unpublished. The
current pin was verified both ways.

Verify before pinning anything, per `.kiro/steering/tech.md`. A BOM needs `-Dpackaging=pom` or the
probe fails misleadingly:

```bash
mvn -U dependency:get -Dartifact=software.amazon.awssdk:bom:2.55.2 -Dpackaging=pom -Dtransitive=false
```

### 4. A Spot interruption fails the build; there is no server-side retry

Found by asking where `EcsTaskSupervisor` actually runs. It does not: the control plane uses only its
static `logStreamNameFor` helper. The supervision loop — which relaunches on interruption and escalates to
on-demand after two — belonged to the deleted direct-ECS path.

Evidence that the retry was intended and not carried over:

- `BuildService` always passes `preferOnDemand=false` to `runTask`; nothing passes `true`.
- `BuildRecord.CellRecord.spotInterruptions` exists with a setter that is never called.
- `BuildMojo` still imports `EcsTaskSupervisor` without using it, and its class javadoc still says each
  cell gets "its own `EcsTaskSupervisor`", which was true only of the direct path.

So `refreshFromEcs` sees a stopped task with a non-zero exit code and marks the cell `FAILED` with the
stopped reason. A reclamation at minute four of a five-minute compile loses the build.

The default is still `spot-preferred`, and the reasoning holds — the window is short and 20 observed tasks
saw no interruption. What changes is the consequence of being unlucky, and deployments that cannot absorb
a lost build should set `-c fargateCapacityStrategy=on-demand-preferred` rather than rely on a retry that
does not run.

Adding server-side retry is the real fix and is not small: a relaunched task has a new task ARN and a new
log stream, so `LogStreamResource`'s per-cell watermarks and the SSE stream both need to follow it — which
is the same hazard commit `7782771` addressed, in a new place.

### 5. MicroVM backend is designed, not built

Two documents, no code: [`microvm-platform-fit.md`](microvm-platform-fit.md) for platform limits and the
client/worker split, [`microvm-build-backend.md`](microvm-build-backend.md) for the design.

The short version: AgentCore Runtime is a fine home for the **client** (2 vCPU / 8 GB is ample for Maven
plus this plugin). Lambda MicroVMs are **ARM64 only**, so they can serve the `arm64` cell and never
`x86_64` — additive to Fargate, not a replacement. The motivation is suspend/resume for PGO, and the
strongest argument is profile *accuracy* rather than speed. Four open questions are listed there, any of
which could sink it.

## Traps worth not rediscovering

* **`RESPONSE_STREAM` Function URLs return 200 on crash.** The runtime error is in the body. Status
  code alone is not a health signal. This hid three startup defects.
* **`git merge --ff-only` prints "Updating x..y" before aborting.** With a dirty working tree it
  reports what it *would* do and then refuses. That output is not confirmation; check `git log -1`.
  This is how `main` silently stayed several commits behind for a while.
* **`findAndRegisterModules()` is a silent no-op** when the module jar is absent. Register Jackson
  modules explicitly so a missing dependency fails compilation instead of the first request carrying an
  `Instant`.
* **`USER 1001:1001` validates nothing**, in Docker or jib. It only sets the uid. The pre-existing jib
  profile shipped a root container unnoticed because of an incorrect comment claiming otherwise. Only
  `scripts/verify-agent-image.sh` actually checks.
* **A `src/test/resources/application.properties` shadows the main one** rather than layering over it,
  and reproduces `SRCFG00027` for an unrelated reason. Use `%test.` overrides in the single file.
* **GitHub PR metadata lags ~10s** after a merge or force-push; `UNKNOWN/UNKNOWN` usually means "ask
  again shortly", not "conflicted".
* **Index-based edits to POMs are how I broke two of them.** There are multiple `<configuration>` and
  `<profiles>` blocks per file; match on surrounding content, not position.
* **XML comments cannot contain `--`.** Broke three POMs.
* **`mvn clean` wipes the function zip**, so `cdk synth` then fails with an opaque asset-staging error.
  `deploy-local.sh` guards this; a manual `cdk synth` does not. It also means `--skip-build` after a
  `clean` deploys a zero-byte zip.
* **ECS rejects an explicit ephemeral storage size below 21 GiB** — `EphemeralStorage size should be at
  least 21`. Fargate's included 20 GiB is what you get by *omitting* the field, not by requesting it. The
  default is 0 for that reason, and `ResourcePolicy` maps any request of 1–20 onto 0.
* **Fargate capacity is server policy, not a client parameter.** `spot-preferred`,
  `on-demand-preferred`, `spot-only`, `on-demand-only`. A client that could demand on-demand capacity
  could raise everyone else's bill — the same reasoning that removed `launchType` from the plugin.
  `spot-only` is a cost ceiling that escalation deliberately will not breach.
* **`native-image` peak RSS is not governed by the Java heap.** It is ~5.4 GB for a 233-jar application
  whether or not `-J-Xmx` is set, because it is dominated by native memory and the image heap being
  constructed. 8 GiB is the floor for that class of project; you cannot configure your way below it.
* **Incremental `mvn install` can leave a stale class.** One run failed with
  `java.lang.Error: Unresolved compilation problems` from inside the plugin jar; `mvn clean install`
  fixed it. Filtering `mvn -q` output by grep is what let it through unnoticed.

## Cost note

The staging bucket and DynamoDB table are `RemovalPolicy.RETAIN` and survive `cdk destroy` by design.
Nothing else in the stack costs meaningfully while idle: no NAT gateways, Fargate tasks are per-build,
and both Lambdas are request-driven. The reaper runs on `rate(1 minute)` and exits immediately when
there is nothing to reap.

If tearing down: `cdk destroy` leaves the bucket and table behind deliberately. Removing them is a
separate, deliberate act.

Renamed from `scaleout-build-maven-plugin`, since the repo holds a Lambda control plane, a container agent,

### GHCR package is public (done 2026-09-29)

`build-agent-image.yml` pushes `ghcr.io/codriverlabs/scaleout-build/scaleout-build-agent` and verifies both architectures
plus the manifest. A GHCR package is **private by default and does not inherit the repository's
visibility**, and `GITHUB_TOKEN` cannot change it — so this needs the UI once per package.

The image path is **nested under the repository**, `ghcr.io/<owner>/<repo>/scaleout-build-agent`, produced
by `ghcr.io/${{ github.repository }}/scaleout-build-agent`. Nesting makes the package owned by the
repository rather than by the org at top level, which is what links it in the repo sidebar and keeps the
workflow's push rights attached without configuring *Manage Actions access* by hand. Using
`github.repository` rather than a literal also means a future rename needs no edit here.

**Nesting also fixed the visibility problem**, which is worth recording because the expectation was the
opposite. The flat org-level package `codriverlabs/scaleout-build-agent` started private and needed a manual
flip. The nested `codriverlabs/scaleout-build/scaleout-build-agent` came out **public on first push, with no
intervention** — a package owned by a public repository appears to inherit that visibility, whereas one
owned by the org at top level does not.

So the manual UI step is not a recurring cost, and is avoided entirely by nesting. Verified anonymously:

```
docker manifest inspect ghcr.io/codriverlabs/scaleout-build/scaleout-build-agent:latest
  -> linux/amd64, linux/arm64, plus 2 attestation manifests
docker run --platform linux/arm64 ... -c 'uname -m; native-image --version'
  -> aarch64, native-image 25.0.4.1
```

The old flat `codriverlabs/scaleout-build-agent` package is now superseded and can be deleted.

Verified anonymously, with no `docker login`:

```
docker manifest inspect ghcr.io/codriverlabs/scaleout-build/scaleout-build-agent:latest       # manifest list, 4 entries
docker buildx imagetools inspect ghcr.io/codriverlabs/scaleout-build/scaleout-build-agent:latest
docker run --platform linux/arm64 ... -c 'uname -m; native-image --version'    # aarch64, Mandrel 25.0.4.1
```

So `install.sh` can copy it into a consumer's ECR, and its pre-flight probe passes.

**On the two `unknown/unknown` entries in the manifest list:** they are buildx *attestation* manifests —
provenance and SBOM — attached by default. They carry no runnable image and Docker ignores them when
selecting a platform, which the `--platform linux/arm64` run above confirms. Expected, not a defect. They
appear in the GitHub package UI alongside the two real platforms, which is the only place they are
confusing.
